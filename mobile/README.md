# スマートフォンから実モデルを試す

公開済みの検証画面: https://origin-pocket-lab.smartghost64.chatgpt.site

同じ ChatGPT アカウントで開き、「編集を試す」または「話しかける」を選ぶ。PC と API キーの入力は不要。学習前・学習後のモデルの切り替え、実際の編集、失敗後の復帰、テスト結果、変更前後のコードを確認できる。

「話しかける」は対話向けの `Qwen/Qwen3-4B-Instruct-2507`（このプロジェクトでの追加学習なし）を使う。「編集を試す」は `Qwen2.5-Coder-0.5B-Instruct` のベースモデルと追加学習した復帰用LoRAを比較する。画面と実行記録には使用モデルを示し、会話用と編集用の接続状態を個別に確認する。

接続は自動で確認する。画面上部の「接続を確認」で再確認でき、スマホに戻ったときと表示中の15秒ごとにも確認する。このボタンは接続状態の確認用で、停止したサーバーの起動は管理者が行う。

フロントエンドは本人専用の Sites、モデルと検証用 API は別の実行環境で動く。モデル用サーバーが稼働している間に実行できる。停止中も「学習の記録」は表示される。

## 実装

- `worker.js`: スマートフォン用画面と同一オリジンの API 中継。接続先と認証情報は Sites の実行環境から読む。
- `scripts/mobile-server.ts`: ローカルモデルに接続する限定された検証用 API。練習課題は一時フォルダーで実行し、終了時に削除する。
- `src/providers/origin-conversation.ts`: 会話専用モデルへの接続と、質問のほぼ同じ繰り返しに対する1回限りの再生成。挨拶や明示的な復唱はそのまま扱う。
- `test/mobile-server.test.ts`: 未認証アクセス、不正な実行種別、会話の道具制限、同時実行の制御を検証する。
- `scripts/check-mobile-conversation.py`: 本人専用の公開APIを通して `conversation-cases.json` の17ケースを実モデルで検証する。認証情報は標準入力からだけ受け取り、レポートに保存しない。形式・キーワード・指定文字数の自動チェック後に回答内容を人手でも確認する。

## 検証用 API の起動（管理者用）

編集モデルを `training/scripts/serve-model.py` で `127.0.0.1:18080` に起動する。会話モデルは次の固定リビジョンを取得し、別プロセスで起動する。

```bash
training/.venv/bin/pip install -r training/requirements-conversation.txt
training/.venv/bin/python training/scripts/download-conversation.py
training/.venv/bin/python training/scripts/serve-conversation.py --port 18083 --threads 2 --generation-timeout 90
```

`unsloth/Qwen3-4B-Instruct-2507-GGUF` の固定リビジョン `a06e946bb6b655725eafa393f4a9745d460374c9`、Q4_K_M版を使う。取得時と起動時に重みのSHA-256を確認する。会話モデルにはLoRAを付けず、`baseline` として推論する。管理者は `ORIGIN_CHAT_MODEL_HOST` で別のループバックHTTPポートを指定できる。APIは会話モデルの種類も接続状態で確認する。両モデルが起動したら次を実行する。

```bash
node scripts/mobile-server.ts
```

標準入力から `token` フィールドを持つ JSON を1行渡す。アクセスキーは32バイトを64桁の16進文字列にした値。API は `127.0.0.1:18081` で待ち受け、全リクエストに Bearer 認証を求める。認証情報をソース、コマンド引数、ブラウザへ埋め込まない。

Sites の実行環境には `ORIGIN_BACKEND_URL` と秘密値 `ORIGIN_BACKEND_TOKEN` を設定する。画面は `/api/health`、`/api/jobs`、`/api/jobs/<id>` だけを中継し、接続先のリダイレクトを追跡しない。サイトの公開範囲は本人専用を維持する。

会話にはファイル・シェル・Web の道具を渡さない。実行できる編集は生成済みの練習課題だけで、任意のコマンドを HTTP から指定する機能はない。実行記録は最大20件、30分の有効期間でサーバーのメモリに保持する。会話履歴はブラウザから直近の数往復だけを送る。

会話には、実際に使える機能に合わせた日本語で返答する指示を渡す。質問をほぼそのまま返したときは回答を一度だけ再生成し、改善しなければエラーにする。返答を定型文に置き換える処理はない。空の回答や未完了の会話は成功扱いにせず、再送できるよう入力を残す。画面の質問例、言い換え、履歴を使う質問などの動作確認と、広い会話能力の評価は別に扱う。

復帰課題では最初の読み取りと拒否された編集を固定してからモデルに続きを任せる。正しい置換先の式は固定の失敗操作に含まれる。この画面での試行は体験用の tune 評価で、未使用 holdout での能力評価とは区別する。

## 2026-10-12の確認結果

`results/2026-10-12-conversation-qwen3.json` に公開API経由の10ケースの実回答を保存した。全件で回答が完了し、質問の繰り返し、挨拶、名前の履歴、要約を確認した。自動チェックは9/10（日常質問は同義表現による不一致）。回答の確認では、コード復帰の説明に変更の保存・テスト手順の省略が残る。開発中に使用した固定ケースであり、一般的な会話能力を保証する評価ではない。

## 日付の扱い

会話の推論ごとにサーバーの時計を読み、ブラウザから受け取ったタイムゾーンで今日・昨日・明日と曜日を計算してモデルへ渡す。端末の日時やユーザーが入力した日付を現在日時として採用しない。タイムゾーンはIntlで検証し、未送信の旧画面や取得できないブラウザではUTCを使用する。日付の情報だけでは天気やニュースなどの最新情報は分からない。

公開APIの検証スクリプトは `case_ids` に確認するケースのIDを指定できる。日付ケースの期待値は、実行時刻と指定タイムゾーンから計算する。年越し・夏時間・うるう日は単体テストでも確認する。

`node scripts/check-conversation-clock.ts` は固定した時計で実モデルの年越し・タイムゾーン差・うるう日など5ケースを検証する。実際の現在日時での検証は `scripts/check-mobile-conversation.py` の `date-` で始まる7ケースを使う。

日付修正の実測は `results/2026-10-12-conversation-clock.json`。公開APIの10ケースと、固定した時計での実モデル5ケースが通過した。修正前の2024年という誤答も同じ会話で再現し記録した。
