# origin-agent

会話する、ネットで調べる、小さなコードを直す。できることが増える過程を楽しむ、自作AIのプロジェクトです。

**v0.9.0 では、ローカルモデルが隔離した作業コピーに origin-agent 自身の修正案を作る試験機能を追加しました。** 修正案はパッチとして保存し、元の作業ツリーには適用しません（[詳細](GROWTH.md)）。
v0.8.2 では、ローカルモデルが長時間考えている間の進捗表示と、コード追加時の編集失敗からの復帰を改善しました。モデルの時間切れでも未完了を明示して回答を返します。
v0.8.1 では、調べものの回答がモデルの時間切れで返らない問題を改善しました。取得済み資料がある場合は、時間切れでも関連箇所と出典を返します。
v0.8.0 では、失敗テストの修正依頼に限り、導入済みの7Bモデルを自動で使えるようにしました。通常の会話や軽いコード作業は3Bのままです。7Bが入っていなければ通常のモデルを使います。
v0.7.0 では、コードを直す作業での小さいモデルのつまずきを、骨格（ツールとエージェントの処理）で受け止めるようにしました。同じ3Bモデルのまま、「バグを直す・関数を足す」課題の成功が 2/9 から 5/9 になりました。
v0.6.0 では、省略した地名や続きの質問でも調べ、資料の数値を確かめて答える処理を追加しました。起動するとローカルのOllamaモデルを探し、会話モードで始まります。呼び方や話し方を保存し、回答への感想を次の関連質問で参照できます。

現在の自然な会話は既存のローカルモデルが担当します。会話や検索によって、モデルの重みが自動で学習されるわけではありません。

## まず話してみる

```powershell
cd C:\Users\6512\development\origin-agent
npm install
npm start
```

このPCには `qwen2.5-coder:3b` が入っているため、Ollamaが動いていれば自動的に選ばれます。
ほかのPCでは [Ollama](https://ollama.com/) を用意し、例えば `ollama pull qwen2.5-coder:3b` でモデルを取得します。
自動選択はインストール済みモデルだけを使い、勝手にダウンロードしません。

起動したら、例えば次のように話しかけます。

```text
こんにちは。私の名前はハルです。
私の名前は何でしたか？
AIを育てるために、今日は何を試したらいいかな？
/search TypeScript とは
```

- `chat` モードでは会話とネット検索ができます。ファイル操作・シェル実行のツールは使えません。
- 会話の内容は起動中だけ保持します。終了・`/reset`・モード変更・モデル変更でリセットされ、長くなった履歴は古いものから省略します。
- 明示して保存した記憶と感想は、終了しても残ります。保存した名前がない場合は、会話中の自己紹介を参照します。どちらにもない名前は作りません。
- Ollamaに接続できない場合やモデルがない場合は `rule` の定型応答で起動し、その制限を表示します。
- 小さいモデルの回答には揺れがあります。試して気づいたことを [GROWTH.md](GROWTH.md) に残していきます。

## 覚えてもらう・忘れてもらう

```text
私のことはハルと呼んで。覚えておいて。
/remember 話し方 短く、やさしく説明して
/memory
/exit
```

再び `npm start` で起動して「私の名前は何ですか？」と聞くと、保存した呼び方を参照します。
「私の名前はハルです」だけの自己紹介は、その会話中だけ使います。

```text
/remember 呼び方 ソラ
/forget 呼び方
```

同じ項目を保存すると更新します。「名前」と「呼び方」は同じ項目です。
記憶を更新・削除したときは会話をリセットします。削除・変更前の値が感想に含まれていれば、その感想も削除して再び参照されないようにします。
「名前を忘れて」でも削除できます。

自然な文章での保存は、呼び方や「短く答えて。覚えておいて」などの限られた言い方に対応しています。
任意の内容は `/remember 項目 内容` を使います。保存できる記憶は50件、1件の内容は500文字までです。

### 回答に感想を付ける

```text
JavaScriptの変数を説明して
/feedback bad もっと短く、例は一つだけにしてほしい
JavaScriptの変数をもう一度説明して
/feedback good この長さが分かりやすい
/feedback list
```

直前に完了した回答の質問・回答・感想・モデル名を保存します。次の関連質問では、同じモードの感想を最大3件読み出してモデルに渡し、「関連する感想を参照します」と表示します。
過去の誤答は回答用の文脈へ入れず、ユーザーの指摘を渡します。一般的な事実についての訂正は未検証の指摘として扱い、出典確認を促します。
関連性は単語や文字の一致で判断する簡単な仕組みなので、言い換えによって拾えない場合があります。

`/feedback delete <ID>` で記録を削除できます。保存は200件までで、いっぱいになると削除を案内します。
感想を渡しても必ずその通りに回答できるとは限りません。モデル自体の追加学習は行いません。

### 保存場所

既定は **作業ルート内の `.origin-agent/learning.json`** です。Gitの対象から除外しています。
記憶と、感想を付けた質問・回答を保存します。作業場所を変えても同じ記憶を使いたいときは、共通の場所を指定します。

```powershell
node src/cli.ts --data-dir C:\Users\6512\origin-memory
```

ファイルが壊れている場合は、空の記憶で上書きせずエラーを表示します。
強制終了の後に「使用中」が続く場合は、同じ保存先を使うoriginをすべて終了し、保存先の `learning.lock` だけを削除して再起動してください。`learning.json` は記憶本体です。

## ネットで調べる

```text
/search TypeScript 公式 とは
つくばみらい市ってどこですか？
みらい平駅の時刻表を教えてください
```

検索語の送信を確認されたら `y` と答えます。必要に応じてページ本文の取得も確認されます。
モデルは検索結果・取得したページをもとに回答し、参照元のURLを付けるよう指示されています。
「ネットで調べて」と普通の文章で頼むこともできます。`/search` はモデルの判断に頼らず、最初に検索を実行する入口です。

### v0.6で増えたこと

```text
大阪ってどこですか？
秋田と岩手ってどっちが大きいですか？
面積はどうですか？
```

- 「府」「市」を省いた地名でも、場所の質問を検索に回します。
- 「秋田と岩手、どっちが大きい？」には県どうしの比較として、面積か人口かを確認します。続く「面積は？」で両県をそれぞれ検索します。市を比べたい場合は「秋田市」のように指定してください。
- 続きの検索に補うのは直前の公開の対象名だけです。雑談などへ話題を変えた後や `/reset` 後は、対象を確認します。
- 検索結果の対象名や項目との関連性で読むページを選び、本文の関連箇所と前後を抜き出します。ふりがなを数値に混ぜないようにしました。
- 資料取得後は今回の質問と資料に集中して回答します。対象名・面積または人口・値・単位が明確な短い文なら、大小はプログラムで計算し、両方の出典を示します。
- 資料にない数値・単位、作られたURL、対象名だけの不十分な回答などは一度見直します。直せなければ未確認と伝えます。

**これは完全な事実確認ではありません。** 数値の照合だけでは、別の対象・時点への取り違えや文章の意味の誤りをすべて防げません。自動計算は限られた書き方が対象で、複雑な表・単位換算・数値の丸めには対応していません。出典自体が古い・誤っている場合もあります。幅広い質問での正確さは、今後の評価と改善の対象です。

### 検索の判断と制限

時刻表・天気・運賃などの移ろう情報や、市・駅・山・寺などの固有の場所、人物についての質問は、言い回しに関わらずプログラムでも判定して検索を始めます。
判定には限りがあり、例えば「イチローの通算安打数は？」は検索に回りません。検索が始まらない場合は `/search` を使えます。
コードモードでも、コードと関係ない事実の質問は検索します。「関数」「ファイル」「src/」など手元のコードについての質問と、「私の〜」「さっきの話」など自分や会話についての質問は、「調べて」と頼まない限り検索しません。
「検索しないで」「オフラインで」と指定した発話では、モデルにもWebツールを渡しません。

自動検索や `/search` が失敗・拒否された場合は、そのことを伝えて終了します。
駅の時刻表は方面・平日と土休日の区別を促し、取得していない発車時刻を作らないよう指示しています。まだ時刻表専用の読み取り機能はありません。

検索には [DuckDuckGoのHTML版](https://duckduckgo.com/duckduckgo-help-pages/features/non-javascript) を使います。APIキーは不要です。
正式な検索APIではないため、認証画面・通信制限・ページ形式の変更で使えないことがあります。その場合は失敗を返し、取得できたふりをしません。
URLが分かる場合は「https://example.com/ を読んで」と頼めます。本文取得は主にHTML・テキスト向けで、JavaScriptが必要なページやPDFの読解には対応していません。

検索は外部サイトへ検索語を送ります。検索結果の抜粋はページ本文とは区別して扱います。

## 小さなコーディングを試す

```powershell
node src/cli.ts --mode code --root C:\path\to\practice-project
```

起動中なら `/mode code` で切り替えられます。

```text
ファイル一覧を見せて
package.json を読んで、どんなプロジェクトか説明して
設定ファイルのポート番号を3000から4000へ変更して
```

ファイルの読み取り・検索・部分編集・コマンド実行などが使えます。書き込み・コマンド実行・外部通信には確認が入ります。
`--yolo` はこれらの確認をすべて省略する既存の実験用オプションです。

`--root` は作業場所の指定です。シェルをOSから隔離する機能ではありません。無人の自己改修は今後、隔離した実験環境を用意してから取り組みます。

### v0.7で増えたこと

```text
src/math.js に、2つの数の積を返す multiply(a, b) を追加して export してください。
src/age.js の isAdult(18) が false になります。18歳以上なら true を返すように直してください。
```

小さいモデルが実際につまずいた形を、`edit_file` などのツール側で受け止めます。ツールの説明文（モデルへの指示）は変えていません。

- **JavaScript を壊した編集は元に戻します。** `.js` / `.mjs` / `.cjs` への書き込みの後に `node --check` で構文を確かめ、元は読めたファイルを読めなくした編集は取り消して、理由をモデルに返します。同じ関数を足し直したときは、すでにある定義の行を示します。元から壊れているファイルは戻しません。`.ts` は型注釈を誤判定するため対象外です。
- **空白や改行の違いは許します。** 複数行の関数を1行に詰めて引用しても、空白と改行を無視して1か所に絞れれば置換します。この場合でも、既存の関数などの定義を消す置換は行いません。
- **`old_string` が空、または省略されたら、ファイル末尾に追加します。**
- **引用が見つからないときは、ファイル内の近い行を示します。** 名前や数値が多く一致する行を、そのまま引用できる形で最大3行返します。
- **改行の二重エスケープと既存関数を消す追加案を指摘します。** 失敗した編集を繰り返さず、末尾追加などの次の手段を選べるようにします。
- 編集やコマンドの後に同じファイルを読み直しても、「同じ呼び出しの繰り返し」と数えません。
- 現在のモードで使えない `web_search` を呼んでも、調べものの失敗として作業を打ち切りません。

**まだ苦手なこと:** テストが落ちている原因を推理して直す課題は、3Bモデルでは 0/3 のままです。モデルはテストを実行して失敗内容を読めても、原因（ループの開始位置のずれ）を見抜けず、見当違いの編集をします。編集の失敗は元に戻せても、正しい直し方を考える部分は骨格では補えませんでした。

### 失敗したテストを直すときの確認（開発中）

コードモードで失敗テストの修正を頼まれ、`package.json` に `test` スクリプトがあれば、まず `npm test` を実行します。出力に現れたテストファイルと、その相対import先の実装ファイルを各1件読み、両方をモデルに渡します。その後、`npm test`・`npm run test`・`pnpm test`・`node --test` などの単独テストコマンドが失敗した状態で編集すると、同じテストを再実行します。テストの実行には毎回通常の確認が入ります。テストが通らなければ再検討を促し、未通過のまま「完了」と報告しません。複数のコマンドをつないだ入力や PowerShell の式を含むコマンドは自動で再実行しません。「テストを実行しないで」という依頼では、自動実行と上記テストコマンドの呼び出しを止めます。

「テストファイルは変更しないで」と指定された修正では、`edit_file`・`replace_lines`・`write_file`・`edit_json` によるテストファイルの変更を拒否します。シェルコマンドは従来どおり実行前の確認が必要です。

この機能はテスト結果を確認するもので、失敗原因を必ず推理できるようにするものではありません。テストを実行していない変更、確認を拒否された再実行、認識対象外のコマンドは自動検証できません。1回ずつの試行では、最初の課題は3Bで失敗・7Bで成功し、別の失敗テスト課題も7Bで成功しました（[記録](GROWTH.md)）。試行数が少ないため、安定した成功率はまだ分かりません。

`/provider auto`（起動時の既定）では、`qwen2.5-coder:7b` が導入済みなら、コードモードで失敗テストの修正を頼まれたときだけ7Bへ切り替えます。切り替え時は使用モデルと待ち時間の注意を表示します。このPCでは2種類の課題を各1回通しましたが、176〜265秒かかりました。モデルをダウンロードしたり、会話全体を7Bに切り替えたりはしません。`/provider ollama <モデル名>` や `--model` で明示したモデルは優先され、自動切り替えを行いません。

### JSONの設定を増やす

練習用の `examples/json-practice/settings.json` を同梱しています。初期状態は次の内容です。

```json
{ "theme": "dark" }
```

プロジェクトのフォルダで次を実行すると、その練習用フォルダを使うコードモードで起動します。

```powershell
npm run practice
```

起動したら、次のように話しかけます。

```text
settings.json に "language": "ja" を追加してください。既存の設定は残してください。
```

`edit_json` を選ぶと、最上位のキー1つを追加・更新できます。追加時は他のキーを残し、更新時は指定した値だけを差し替えます。
モデルはファイル全体を引き写す必要がありません。文字列のほか、数値・真偽値・null・配列・オブジェクトを値として渡せます。
空白や既存の数値表記は保持し、変更前に対象キーと値を表示して確認します。確認中にファイルが変わった場合は書き込みを止めます。

対象は200KB以下の、最上位がオブジェクトの通常のJSONです。コメント付きJSON、最上位キーの重複、入れ子の中のキーを指定する操作には対応していません。
`key` のドットは文字どおりの名前です。既存のオブジェクトを値として指定すると、そのキーの値全体を置き換えます。
モデルが別の編集ツールを選ぶ場合もあるため、確認画面と変更結果を見てください。
専用ツールの説明は、依頼に `.json` があるとき、またはJSONファイルを読んだ後にモデルへ渡します。直前に読んだり、このツールで編集したJSONへの続きの依頼にも使えます。
別のファイルへの依頼では、指定や読み取った対象に合わせて道具を切り替えます。会話のリセット時には、読み取った対象の記憶もリセットします。

## コマンド

| コマンド | 内容 |
|---|---|
| `/search <検索語>` | ネット検索を実行して回答する |
| `/remember <項目> <内容>` | 記憶を保存・更新する |
| `/memory` | 保存した記憶を確認する |
| `/forget <項目>` | 記憶と、その値を含む感想を削除する |
| `/feedback good [感想]` | 直前の回答のよかった点を保存する |
| `/feedback bad <改善点>` | 直前の回答の改善点を保存する |
| `/feedback list` | 最近の感想とIDを表示する |
| `/feedback delete <ID>` | 感想を削除する |
| `/mode chat` | 会話・検索モードへ切り替え、会話をリセット |
| `/mode code` | コーディングモードへ切り替え、会話をリセット |
| `/provider auto` | 通常のモデルを自動選択し、失敗テストの修正時は導入済みの7Bを使用 |
| `/provider ollama <モデル名>` | 指定したモデルを使う |
| `/provider rule` | 学習を使わない定型応答に切り替える |
| `/tools` | 現在のモードで使えるツールを表示 |
| `/stats` | 前の応答時間・最初の表示・モデルの処理時間を表示 |
| `/reset` | 会話をリセット（保存した記憶・感想は残る） |
| `/help` | コマンド一覧 |
| `/exit` | 終了 |

起動オプションは `node src/cli.ts --help` で確認できます。

### rule で試せること

`こんにちは`、`ありがとう` に定型応答します。`web <検索語>` と `fetch <URL>` は結果をそのまま表示します。
自由な会話や検索結果の要約には、Ollamaなどのモデルが必要です。

`code` モードでは `ls`、`read <パス>`、`search <正規表現> [glob]`、`write <パス> <内容>`、`run <コマンド>` も使えます。
`edit_file` は定型ルールでは呼べません。

## 反応が遅いとき

普通の会話は、生成された文字から順に表示します。調べものは数値・出典の検査後に文章を表示します。比較の条件確認と、資料から明確に読み取れる数値の大小計算は、モデルを呼ばずに処理します。
モデルから文字が届かない間は30秒ごとに使用モデルと経過時間を表示します。待ち時間の上限に達したときは、未完了であることと再試行方法を回答として表示します。
資料から回答する段階では生成量を抑え、既定の待ち時間を60秒にしました。時間切れでも、取得済み資料に質問と関連する文があれば、要約に代えてその文を出典付きで引用します。資料が取得できていない場合は回答を作りません。`ORIGIN_OLLAMA_TIMEOUT_MS` で待ち時間を明示した場合はその値を優先します。
更新前から起動している端末には変更が反映されません。`Ctrl+C` で停止し、`C:\Users\6512\development\origin-agent` で `npm start` を実行してください。
これは待ち時間の見え方を改善する機能です。モデルが考えたり文章を作ったりする計算自体は引き続き必要です。
ツール構文やコードの開始が見えた場合は、その先を完成まで待ってから表示します。最終回答を二重表示せず、通信が途中で切れた未完了の回答は会話履歴へ追加しません。
実装は [Ollamaのストリーム応答](https://docs.ollama.com/api/streaming) に対応しています。

遅いと感じた回答の後に、次を入力してください。

```text
/stats
```

- **最初の表示**: 質問してから、回答の文字が出始めるまで。
- **モデル読み込み**: モデルを使える状態にする時間。起動直後や、モデルを切り替えた直後は増えることがあります。
- **入力の処理**: 会話履歴や指示をモデルが読む時間。
- **文章の生成**: 回答を作る時間。長い説明や、複数回のツール判断は時間がかかります。

「全体」の時間には、ネット検索・ツール処理・確認への返答待ちも含みます。モデルの内訳は、完了した呼び出しごとに表示します。
現在のPCではOllamaのGPU使用メモリが0で、3BモデルはCPUで動作していました。まず既定の3Bで短い会話を試し、どこに時間がかかったかを見ると改善箇所を絞れます。
モデルやPC、キャッシュの状態が変わると速度も変わるため、名前の記憶のようにプログラムだけで答える質問と、モデルが文章を作る質問は分けて比べます。

```powershell
npm run bench:response -- --repeat 2 --out response.json
# 一括表示との比較。モデル名・指示・質問は同じにする
npm run bench:response -- --buffered --repeat 2 --out buffered.json
```

この計測は3つの短い質問を各2回、独立した会話としてモデルへ送ります。最初の表示、回答完了、出力全文、モデルの処理時間を保存します。
ネット検索や個人の記憶は使いません。最初の実行は読み込みや入力キャッシュの影響を受けるため、結果の平均だけでなく各回答も確認してください。

## 成長を確かめる

```powershell
npm test                 # モデルなしで、ツール・モード・通信の失敗時などを確認
npm run typecheck
npm run check:live       # ローカルモデルで会話→名前の確認→実際のネット検索を試す
npm run check:research -- --repeat 2  # 資料を固定して、読解・比較・未確認を検査
npm run check:research -- --live      # 画像と同じ会話を、実際の検索で検査
npm run check:code       # 一時フォルダの設定値を1つ変更できるか試す
npm run check:growth     # v0.3の記憶・感想の参照・地名と時刻表の自動検索を試す
npm run eval -- --offline --repeat 3 --out growth.json  # 同じ課題を繰り返して成績を保存
```

`check:live` は既知の検索語「TypeScript 公式 とは」を送信し、モデルが必要と判断した公開ページも取得します。
会話モードのためファイル操作はできません。名前の確認、日本語の回答、取得結果に存在するURLの参照を機械的に確認し、会話も表示します。
これは小さな動作確認です。回答内容の正しさや、幅広い課題への能力を保証するテストではありません。
別のモデルを比較するときは `npm run check:live -- <モデル名>` を使います。

`check:research` は画像の3往復、架空の市の比較、資料にない人口、比較順序の逆転を検査します。既定ではWeb部分を固定資料に置き換え、モデルとエージェントの処理を再現可能にします。数値比較がプログラムで完了したケースは、モデル単体の成功ではありません。
`--live` のときだけ実際の公開ページを検索・取得します。固定資料と実検索の結果は別ファイルに保存します。`--out <ファイル>`、`--repeat <1〜10>`、`--model <モデル名>` を指定できます。使用する記憶は検査用の一時フォルダです。

`check:code` は一時フォルダの `config.json` で、指定値の変更と無関係な設定の保持を確認します。
シェル・ネット・全文上書きのツールは渡さず、一時ファイルを終了時に削除します。小さいモデルでは失敗することもあるため、改善前後を比べる練習課題として使います。

`check:growth` はユーザーの記憶とは別の一時フォルダで、保存・読み戻し・削除、感想の参照、実際の地名・時刻表検索を試します。
名前の確認はプログラム側の処理、説明文の生成はモデルの処理です。モデルだけの能力評価と混同しないよう、出力にも区別して表示します。
このコマンドは公開情報の検索語を送信し、必要に応じて公開ページを取得します。

### 採点結果から次の改善を選ぶ

```powershell
# まず、苦手な小さな編集を測る
npm run eval -- --only add-field,preserve-rest --repeat 3 --timeout 300 --out before.json

# ツールや指示を改善した後に、同じモデル・課題・条件で比較する
npm run eval -- --only add-field,preserve-rest --repeat 3 --timeout 300 --compare before.json --out after.json

# 別の設定ファイルや値の種類でも確かめる
npm run eval -- --only json-flag,json-array --repeat 3 --timeout 300 --out transfer.json
```

JSONの `tasks[].attempts[].trace` には、各試行の質問・ツール引数・実行結果・回答・終了理由が残ります。
失敗した試行でも操作を追えるため、「何も編集しなかった」「違う値に置き換えた」「確認が足りなかった」を区別できます。

### 採点の文面を覚えただけになっていないか確かめる

「検索に回すか」の判定はモデルを使わない関数なので、言い換えへの強さを数ミリ秒で測れます。

```powershell
npm run eval:route               # tune: 判定を直している間はこれだけを見る
npm run eval:route -- --holdout  # holdout: 直し終わってから1回だけ見る
```

質問集 `scripts/route-cases.ts` は、見ながら直してよい `tune` と、直している間は見ない `holdout` に分かれています。
以前の判定は採点課題の「〜ってどこですか？」だけを検索に回し、「〜ってどんな場所？」と言い換えると記憶で答えて「広島県」と捏造しました。
tune だけを見て直すと成績は必ず上がるので、本当に良くなったかは holdout で確かめます。
holdout の失敗を見て規則を直したら、その質問は tune に移し、holdout には新しい質問を足してください。
判定を直す人とは別の人（理想は普段この道具を使う本人）が holdout を書くのが一番確かです。

モデルを使う能力テスト（`npm run eval`）にも holdout の課題があります。v0.7 で足した「コードを直す」課題の半分です。

```powershell
npm run eval -- --offline --repeat 3 --out tune.json   # 既定では holdout を含めない
npm run eval -- --holdout --repeat 3 --out holdout.json  # 直し終わってから1回。合計だけを表示する
```

`--holdout` は課題ごとの内訳や失敗理由を画面に出しません。落ちた課題を見ると、それを通す規則を書いてしまうためです。保存したJSONには残るので、見て直した場合はその課題を tune に移してください。
`tasks[].tools` で登録した道具も確認できます。モデルへ渡す説明は、モードや編集対象に応じてさらに絞ります。
採点は課題ごとに途中保存し、最後まで終わると `completed: true` になります。
この記録は評価用の会話です。普段の会話を自動で保存する機能ではありません。

通常の採点では一時フォルダを使い、編集課題にネット・全文上書きツールを渡しません。シェルは、テストを実行する「コードを直す」課題にだけ渡します。
`--offline` を外すと公開情報を検索する課題も含みます。`--min 0.8` のように指定すると、合計成功率が基準未満のとき終了コード1になります。
自動採点は決めた条件の確認であり、文章全体の正しさの保証ではありません。名前の記憶などはプログラム側の処理も含むため、合計だけでなく課題ごとの成績を見ます。
今は改善の採用判断を人が行います。将来の自動改善では、独立した課題での確認と悪化した変更を戻す仕組みをここに足します。

次の成長段階と実験の記録は [GROWTH.md](GROWTH.md) にまとめています。

```text

  learning.ts          記憶と感想の保存、関連する内容の検索
  routing.ts           自動検索する質問の判定
  retrieval.ts         関連するページの選択、本文の関連箇所の抜粋

  comparison.ts        明確に記載された2対象の数値を比較
  agent.ts             会話・ツール実行のループ、モード制限、履歴管理

  types.ts             Provider・Tool・Messageの型
  protocol.ts          モデルへの指示、<tool>形式の解析

  providers/
```

ツール呼び出しは `<tool>` ブロックで表現し、自作モデルも同じ形式で接続できます。

## 自作モデルと自動改善への道

### 自分自身の修正案を作る（試験機能）

```powershell
npm run self:propose -- --goal "edit_file の失敗後に同じ操作を繰り返さず、次の手段を選べるようにする" --attempts 2 --minutes 60
```

導入済みのローカルOllamaモデルだけを使います。`--model` で変更できます。作業ツリーがクリーンな場合に限って一時的なGit作業コピーを作り、モデルには `src/` の既存ファイルへの編集だけを許します。シェルやWebのツールは渡しません。生成した差分と操作履歴は `.origin-agent/proposals/` に保存します。Windowsでは実行中だけスリープを防ぎます。

**修正案は未検証です。** このPCには候補コードを隔離して実行する環境がまだないため、候補を自動実行・採点・採用・プッシュしません。モデルの重みも学習しません。無人での採用には、隔離環境で固定テストと別課題を走らせ、悪化した案を破棄する段階が必要です。

### 長期的な目標

エージェント本体とモデルの両方を育てます。

1. 会話と調べものを試し、小さな「できた」を増やす。
2. 実行記録・ユーザーの感想・能力テストを整える。
3. 過去の経験を保存し、必要なときに参照する。
4. 小型モデルの実装・学習・保存・生成を一から試す。
5. 自作モデルを `Provider` で接続し、既存モデルと同じ課題で比較する。
6. 改善案を実験環境で試し、独立した評価でよくなった候補だけを採用する。

小型モデルを自作して限定した能力を伸ばすことから始めます。汎用的なコーディング能力を高めるには、データ・計算資源・検証の積み重ねが必要です。
会話で参照できる「記憶」、モデルの重みを変える「学習」、プログラムの「改修」は、それぞれ別の仕組みとして作ります。

## 実測: 骨格だけで結果がどう変わったか

同じ `qwen2.5-coder:3b` に、同じ指示
（「ollama プロバイダの既定モデルを 7b から 3b に変更して」）を与えた記録。

| 回 | 結果 | 直した骨格 |
|---|---|---|
| 1 | `ollama.yaml` という実在しないファイルを捏造し、諦めてユーザーに手順を指示 | 作業ルートの見取り図を渡していなかった |
| 2 | 同じ `edit_file` を延々と繰り返し、10分以上暴走 | ループ検出を追加。`search` の path にファイルを渡すと黙って「一致なし」を返すバグも修正 |
| 3 | 正しいファイルには到達。しかし実在しない行を捏造 | 「あなた自身が直す。ユーザーに依頼しない」を明示。エラー文で正規表現を名指し |
| 4 | `write_file` で 79 行のファイルを捏造した 3 行に置き換え、「完了しました」と報告 | **`write_file` が既存ファイルを既定で上書きしないようにした** |
| 5 | **成功。** 66 行中 1 行だけを正しく置換（49.8 秒） | — |

5回目を決めたのは 4 の変更でした。全文書き換えという逃げ道を塞いだ結果、
モデルは `edit_file` を正しく使うしかなくなりました。

ここから引き出せる原則:

- **骨格はモデルを補助するだけでなく、モデルから守る側でもある。**
  確認プロンプトは `--yolo` で飛ぶが、ツールが自分に課す関門は飛ばない。
  危険な操作は、人間への確認ではなくツールの契約で縛る。
- **エラーメッセージは、モデルにとっては次の指示。**
  「見つかりません」で終えると同じ引数で再試行してくる。何をすれば回復できるかまで書く。
- **賢さの多くは、モデルではなく文脈の設計から来る。**
  見取り図を渡すだけで、捏造したパスが正しいパスに変わった。
